## 通知页评审 · GitHub 通知 API 能力核实（18:50）
- 结论：GET /notifications 一个接口即可返回全部通知类型（Issue/PullRequest/Discussion/Release/Commit/RepositoryVulnerabilityAlert/CheckSuite/RepositoryInvitation…），按 most recently updated 排序。
- 但只给线程元数据（subject.title/type/url/latest_comment_url、reason、unread、updated_at、repository）；正文与评论要按 subject.url 按类型二次请求。
- reason 枚举 15 种：assign/author/comment/ci_activity/invitation/manual/member_feature_requested/mention/review_requested/security_advisory_credit/security_alert/state_change/subscribed/team_mention/approval_requested。reason 会随线程变化（author → mention 后保持 mention）。
- 写操作：PATCH /notifications/threads/{id} 标记已读；PUT /notifications 全部已读（可能 202 异步）；DELETE /notifications/threads/{id} 标记 done；threads/{id}/subscription 静音。
- 轮询：Last-Modified / If-Modified-Since → 304 不耗限额；响应头 X-Poll-Interval 给出允许的最小轮询间隔（须遵守，通常 60s）。
- ⚠️ 关键限制：该组端点只支持 classic PAT（scope notifications 或 repo），不支持 GitHub App user/installation token，也不支持细粒度 PAT —— 直接影响「OAuth App → GitHub App」迁移计划（见 MEMORY.md）。
- 邮件通知 ≠ API 通知：邮件头里的 reason 有 push / your_activity，API 的 reason 列表里没有。

## 技术文档前置调研：认证方案（21:05-）
- 用户提问「OAuth App + classic PAT 的『权限较粗』是什么意思」→ 用 SVG 对比图说明：classic `repo` scope = 账号级 + 资源包级（覆盖全部仓库的代码/分支/Webhook/Deploy Key），无法限定仓库、无法只给单一资源；fine-grained 才能仓库级 + 资源级三档。

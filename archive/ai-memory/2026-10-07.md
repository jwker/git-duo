## 切片 5 之 5.1 —— 领域层 `GitDuoKit/Search/`（+71 项）

### ⚠️ 本步最重要的一件事：一条旧设计被官方事实推翻（决策 #47）

查"代码搜索需 ≥1 非限定词"时**顺带**撞到另一条官方限制，它把 §9.2 的既有写法直接作废：

> For requests made by **GitHub Apps with a user access token**, you can't retrieve a combination of
> issues and pull requests in a single query. Requests that don't include the `is:issue` or
> `is:pull-request` qualifier will receive an **HTTP 422**. To get results for both issues and pull
> requests, you must **send separate queries**.
> —— `docs.github.com/rest/search/search`（current / GHES 3.5 / 3.13 / 俄文版**四处同句**）

本项目用的正是 **App 用户令牌（`ghu_`）** ⇒ §9.2 原写的「一次 `GET /search/issues`、按类型字段区分」

## 本轮最有价值的两条教训（都进了 `MEMORY.md`）

### ① 行内代码的闭合必须**等长**，不能只找"下一个反引号"

原实现遇到 `` ` `` 就找下一个 `` ` `` 配对。于是 `` ``` swift ``` extra `` 里三个反引号被错配成一对，
**吃掉两个字符**（内容被改，但页面上完全看不出来 —— 没有报错、没有视觉异常）。

可重复的（反引号、`~`、引号）必须按 run length 匹配。

### ② 词法扫描器：**起始字符集合必须 ⊆ 后续字符集合**，否则死循环且症状是 SIGKILL

⚠️ **本轮最贵的一个坑**：`swift test` 整个进程被 **SIGKILL（exit 137）**，
输出在 `◇ Test run started.` 之后**什么都没有** —— 看起来像"环境坏了 / 沙箱又有问题"。

真因：`SyntaxHighlighter.scan` 的标识符分支**起始**字符集合含 `@`（为了 `@available` 一类），
而**后续**字符集合 `isIdentifierBody` 不含 ⇒ `@available(…)` 走进去后 `while` 一步不跑、`index` 原地不动 ⇒ **死循环**（0.2 秒吃满 CPU 被系统杀掉）。

定位路径（值得复用）：`swift build` 正常 ⇒ 只跑 `--filter MarkdownParserTests` 通过 ⇒ 只跑 `--filter SyntaxHighlighterTests` 立刻 137 ⇒ 锁定文件。
**判据：`swift test` 无输出地被杀，先查死循环，不要先怀疑沙箱**（沙箱问题的症状是"有报错、报的是 sandbox_apply"，不是"没有输出"）。

修法三件：
1. `isIdentifierBody = isIdentifierStart(character) || character.isNumber` —— 两集合的关系由断言守住（`identifierStartImpliesBody` 遍历候选字符）。
2. `defer { if index == iterationStart { index += 1 } }` 作**结构性兜底** —— 以后再加分支忘推下标，最坏是"少染一个字符"而不是"跑不动"。
3. 新增守卫测试。

顺带修掉的同类三处：`0x1F` 被切成 `0` + 标识符 `x1F`（`isHexDigit` 不含 `x`）⇒ 数字分支特判 `0x`/`0b`/`0o`；
`1..<5` 的 `..` 被吃进数字 ⇒ 遇连续两个 `.` 即中断。

## 三处「按实测形状写」而不是「按文档措辞写」

1. **`RepoContentType` 不能是 `String` 枚举** —— GitHub 目录项的 `type` 取值是 **`"dir"`**，不是 `"directory"`。
   靠自动合成的 `init(rawValue:)`，**每一个目录**都会掉进兜底档 `.unknown`。
   症状不是报错，是"整个文件树点不动"。已改手写 `switch(rawType:)` 并同时认 `dir` / `directory`。
   ⇒ 这是本轮**第一个**"照文档措辞写就错"的点，也是唯一一个**必须读真实响应**才看得出来的。
2. **`CompareDTO` 根本不声明 `commits` / `files`** —— 服务端对这两个数组有截断，
   判"有没有未合并提交"只能读 `ahead_by`。不声明 = "想数也没得数"，顺带省掉可能几十 KB 的无用解码。
3. **`MergeOutcome` 而不是 `MergeResultDTO?`** —— 204「没有东西可合」是**确凿的正面答案**，

## 配额桶：显式声明 + 正面守卫

14 条路由全部显式写 `rateLimitResource: .core`。⚠️ **漏声明不会有任何报错**（默认值就是 `.core`、间隔 0 = 不限速），
所以新增 `RepoEndpointQuotaTests`：给限流器一份**"每个桶间隔都非 0"的探针策略**，于是可以**正面**断言
"这条路由落了主桶 **且** 没误用 Search 桶"。

> **判据**：配额/桶这类"默认值恰好也正确"的声明，守卫要**让默认值变错**（把每个桶都设成有限速），
> 否则 `.core` 与"压根没声明"给出**同一个结果**——那种断言永远绿，比没有还危险。

## ⚠️ 真缺陷：CRLF 提交信息（6.1 遗留，已修）

**症状**：`firstLineRuleIsShared` 两条断言失败 —— 目录行副标题得到的是整段（含 `\r\n\r\n正文`），详情页 `body` 得到 `nil`。

**排查**：写 `/tmp/probe.swift` 实测，`parts.count = 1` —— **一刀都没切开**。

**真因（语言事实，不是逻辑错）**：**Swift 把 `\r`、`\n`、`\r\n` 当作三个互不相同的 `Character`**
⇒ 按 `"\n"` 拆分**永远匹配不上 CRLF**，`"fix: x\r\n\r\n正文"` 被当成一整段没有换行的信息。

**后果为什么难发现**：不报错、不崩，只是"内容拼错了"——副标题里标题与正文挤成一段、详情页正文整块消失，
**单看任何一处都正常**。GitHub 上确有用 Windows 编辑器提交的仓库，`\r\n` 是真实输入，不是假想。

**修法**：`CommitMessage.normalized(_:)` 先 `replacingOccurrences(of: "\r\n", with: "\n")`，
与 `FileContent.lines(of:)` / `UnifiedDiffParser` 走**同一套规矩**（那两处一直是这么做的 ⇒ 只有这一处漏了）。
归一**集中在一个函数里**（而不是内联两处）是有意的：`grep "\r\n"` 才查得出来。

**影响面排查**：包内"按行拆"共三处 —— `FileContent.lines(of:)`、`UnifiedDiffParser`、`CommitMessage`。
前两处本来就先归一，**只有第三处受影响**。

**新增 `CommitMessageTests`（10 项）**，其中一条**钉的是根因本身**：
```swift
#expect("\r\n".count == 1)                       // 语言事实
#expect("a\r\nb".split(separator: "\n", maxSplits: 1, omittingEmptySubsequences: false).count == 1)
```
这条不是"测我们的代码"，是防止将来有人把归一当冗余删掉。

**另一条**：`归一只认 \r\n：单独的 \r 不是行尾`（与 git 的 `%s` 一致）—— 我们不是在发明换行规则。

## 这条缺陷是"不变量断言"抓出来的（方法论）

`firstLineRuleIsShared` 的本意只是钉"三处显示必须一致"（目录行 / 列表行 / 详情页），
它**不关心** CRLF、也不检查任何具体文案 —— 结果正因为三处共用一份实现，差异一出现就露了。
⇒ **"三处必须一致"这类不变量断言，比"逐处断言期望值"更容易发现真缺陷**：前者不需要预先想到 CRLF 这个输入。

## 几处有意的设计取舍

- **`deleteBranch` 的缓存失效是粗粒度的**（按路径前缀匹配、不看查询串）⇒ 会清掉该仓库所有分支的 contents/commits。
  有意如此：分清 `?ref=` 需要把查询串纳入缓存键的语义，而"多几个请求"比"删完分支后一直 404"轻得多。
- **`latestCommit` 的 404 不吞**：吞了 ⇒ 副标题静默留白，而 §9.4.1 的分支回落**本应被这次 404 触发**。
  唯一允许吞 404 的是 `readme`（仓库没 README 是正常情况）。
- **`readme` 非 UTF-8 抛错、不返回空串**：返回空串 = "README 是空的"，与事实不符。
- **建分支的请求体形状 ≠ 响应形状**：请求 `{"ref", "sha"}`，响应把 sha 包进 `object` ⇒ 不能共用一个 DTO。
- **三个写操作一律不自动重试**（`.sending(…)` 路径）：`POST /git/refs` 重放一次可能建两条同名分支。
- **`repository(owner:repo:)` 与探索页的同名端点不合并**：打同一条路由、解同一个 DTO，但**语义不同**（可写详情 vs 只读探索）。

## 四、⚠️ 6.4e 修掉两条真缺陷（都是"单看哪一处都不报错"，都是被本片新写的单测钉出来的）

先写断言、**跑一遍看它红**，再修 —— 两条都走完了这个流程。

1. **`size` 未知时图片会被整张拉进内存**：从提交详情点进一个文件时调用方**只有文件名**，
   `FilePreviewKind.decide(name:size: nil)` 按**名字**那一侧处理 ⇒ 图片一律判 `.image`，

   一张 20MB 的 PNG 会被整张拉进内存，只为发现它太大然后丢掉。
   修法**不是**把判定挪到发请求之后：第一趟 `contents` 本身就是为了拿判据（它只回元数据、不拉字节流）；
   **重判落在第二趟（raw）之前**，那一趟才是可能拉大字节流的那趟。文本侧不受影响。
2. **0 字节的文件被判成 `.undecodable`**（显示"这个 App 不认识它的编码" —— **假话**，
   而且用户连那个空文件都看不到）。链路：空文件回 `size: 0` + `content: ""` ⇒ `isContentOmitted`
   **放行**（对：空文件走 raw 只会拿回同样一个空串）⇒ 但 `decodeBase64("")` 返回 **`nil`**
   （这条约定**是对的**，`FileContentCodecTests` 正面钉着它）⇒ `content.flatMap(…)` 也是 `nil`
   ⇒ 落进"解不出来"那一档。**修法是在 `loadInlineText` 里把"零个字节"显式认出来**
   （`text(from: Data())` 是合法的空串、不是失败），**不是**去改 `decodeBase64`。
   ⚠️ 这条正是 `.unsupported`（没下载）与 `.undecodable`（下载了）**必须分档**的意义所在。

"二进制零请求""图片超限零请求""重判用同一阈值""空壳补 raw""空文件不是解码失败""GBK ⇒ `.undecodable`"

## 6.7 目视修复（第 1 批 · 用户报回 5 条）

### ✅ 第 1 条 —— 首页「清除」弹层位置不对

### ✅ 第 2 条 —— README 里的 HTML 标签原样显示

- **取证**：拉真实 README（`anywhere-labs/dsh-desktop`，default branch **`master`**）逐字核对 ——
  首屏就是 `<p align="center">` + `<h1 align="center">` + `<img>` + `<sub>` + `<br>`，后面还有 `<details>`/`<summary>` 与多张 `<table>`。
- **定性**：查 `TECH_SPEC §11.1` 发现「内嵌 HTML」原本列在**「不做」**里，而原型那条 README 是**写死的 HTML**
  ⇒ "看起来支持"是**演示数据假象**。⇒ **改口径，不是当 bug 硬修**；文档要写清"**是文档口径错、不是实现错**"。
- **修法**：新增 `Packages/GitDuoKit/Sources/GitDuoKit/Rendering/MarkdownHTML.swift`
  （HTML 块 → Markdown 源的**纯函数**）+ `MarkdownParser` 里一个 **④.5 HTML 块**分支
  （**改写后复用同一解析器**，不另写一套产块逻辑）。
  - ⚠️ **收尾条件是空行**（CommonMark 6 / 7 型），不是 `</div>`。
  - ⚠️ `htmlBlockStart` 必须要求**同一行里有收尾的 `>`** —— 否则一行残缺的 `<b` 会被反复判成 HTML 块（**递归不收敛**）。
  - ⚠️ `markdown(from:)` 走**两趟**（第一趟去标签 + 映射 + 还原实体，第二趟**只**去标签）：
    第二趟是必须的，否则"还原出 `<div>` → 又被当 HTML 块"**递归不收敛**。
  - 映射表：`h1`–`h6`→`#` · `br`→空行 · `img`→`[alt](src)`（`alt` 空则整张丢）· `a`→`[文字](href)` ·

### 用户报回：「我创建了一个『～』的分支，成功了」——判定**不是缺陷**，但隔壁探到一个真缺口

用户用目视时随手试了一个名字。**结论：`～` 被放行是正确行为**，三层证据一致：

| 名字 | 客户端 `BranchName.validate` | `git check-ref-format` | GitHub API | 一致？ |
|---|---|---|---|---|
| `~`（U+007E 半角） | 拒绝 `forbidden(~)` | **拒绝** | — | ✅ |
| **`～`（U+FF5E 全角）** | **通过** | **接受** | **201 建成功**（用户实测） | ✅ **一致** |
| `〜`（U+301C 波浪线） | 通过 | 接受 | — | ✅ |
| `a b`（半角空格） | 拒绝 | 拒绝 | — | ✅ |
| `a\u{00A0}b`（不间断空格） | 通过 | 接受 | — | ✅ |
| `a..b` / `x.lock` | 拒绝 | 拒绝 | — | ✅ |
| `@{` | 通过（**有意**，规格八条不含它） | 拒绝 | 422 | ❌ 已知偏差、待裁定 |
| **`~\u{0301}`（`~` + 组合重音）** | **通过** ← ❌ | **拒绝** | 会 422 | ❌ **本轮新发现的真缺口** |

- `forbiddenCharacters` 是**照 git 抄的 ASCII 字符集**（`" " ~ ^ : ? * [ \` 八个）⇒ git 只禁 **ASCII** `~`，`～` 是另一个码位、git 与 GitHub 都接受。
  ⇒ **服务端与客户端一致**，不存在"文档说可以、App 说不可以"或反过来。**用户看到的"成功"是实情**。
- **能不读得回来**也实测过（这才是容易挂的地方）：`GitHubRESTClient.url` 用 `URL.appendingPathComponent`，
  非 ASCII 会自动百分号编码 ⇒ `～` → `%EF%BD%9E`，三条链路都正确：
  `…/git/refs/heads/%EF%BD%9E` · `…/compare/%EF%BD%9E...main` · `…/contents?ref=%EF%BD%9E`。

**⚠️ 新发现的真缺口（本轮唯一，代码未改）**：`~\u{0301}` 在 Swift 里是**一个字素簇**（`"~\u{0301}".count == 1`），
而判据 `name.first(where: { forbiddenCharacters.contains($0) })` 是按 `Character`（字素簇）比 ⇒ **放行**；
但 URL 编码出来是 `~%CC%81` —— **ASCII `~` 原封不动进了请求**，git 拒、服务端 422。
**这正是 `BranchName` 文档里写明它存在的那条理由**（"某个名字在客户端放行、到服务端吃 422"）。

⇒ 是**一整类**、不是孤例：任何"禁用字符 + 组合记号"都被漏（`^\u{0301}` · `?\u{0301}` · `[\u{0301}` …）。
反证：`\u{0301}~`（组合记号在前）是 **2** 个字素簇 ⇒ 被正确拦下 —— **拦不拦全看组合记号的写法，而用户看不出差别**。
⚠️ 修法只能是**按 Unicode 标量（≈ 字节）判**，不能按字素簇判；对照控制字符那条**本来就是按 `unicodeScalars` 判的**（只有禁用字符这条不是）。
⚠️ 顺带一处小瑕疵：`~` 的提示语把 `~` **印了两遍** ——
`"分支名不能包含 \(character)、空格，以及 ~ ^ : ? * [ \\ 这些字符"` ⇒ 输出 `分支名不能包含 ~、空格，以及 ~ ^ : ? * [ \ 这些字符`。

### 6.8 分支名校验 · 按 Unicode 标量判（用户裁定「按你的建议修」）

**起源**：用户在目视时自己在「新建分支」里连试 `～` 与 `？` —— **两个都建成功了**。
先判性质，**结论：全角字符被放行是正确行为**，三层证据一致（客户端 / `git check-ref-format` / GitHub API）。
⚠️ 但顺着这条探到一个**真缺口**，本轮把它修了。

**改了什么（两处，都在 `GitDuoKit/Branches/BranchName.swift`）**
1. **禁用字符判据从「按 `Character`（字素簇）」改成「按 `Unicode.Scalar`」**
   - 病根：`"~\u{0301}"` 在 Swift 里是**一个**字素簇（`.count == 1`）⇒ `name.first(where: { set.contains($0) })` 拿到整簇、与 `"~"` 不相等 ⇒ **放行**；
     而 URL 编码出来是 `~%CC%81` —— **ASCII `~` 原封不动进请求** ⇒ git 拒、服务端 **422**。
   - 漏的是**一整类**（任何「禁用字符 + 组合记号」）；反证 `"\u{0301}~"`（记号在**前**）是两个字素簇、原本就拦得住
     ⇒ **拦不拦只看记号写在哪一侧，而屏幕上两者几乎一样**。
   - ⚠️ **这正是 `BranchName` 开头写明它存在的那条理由**（"某个名字在客户端放行、到服务端吃 422"）；
     写在文档里的风险，这次真的发生了 ⇒ 可见"文档里写了"不等于"挡住了"。
   - 正本从 `Set<Character>` 改成**有序 `[Unicode.Scalar]`**（`forbiddenScalars`），判定用它的 `Set` 视图**现算**（避免"加禁字符只改一处"）。
     ⚠️ **有序是有用的**：提示语要按固定次序列举，集合顺序每次不同会让人以为换了一条规则。
2. **提示语把命中字符印两遍** —— 原先写死一段字符表，命中 `~` 时成了
   （`分支名不能包含 ~、空格，以及 ~ ^ : ? * [ \ 这些字符`）。改为从正本**排掉命中项现算**（`remaining(_:excluding:)`）。

**没改什么（有意为之，都不是漏）**
- **全角同形字照旧放行**（`～` `？` `＊` `：` `＾` `［` `＼` `｜` · 全角空格）：它们是独立码位、git 收，拦了就是"实现比规格严"（与 `@{` 同一种越界）。
  ⚠️ 用户的选择是**最小修**："只按标量判（只堵真缺口、不新增任何规则）"，不是"再拦同形字"。
- `@{` **维持原判不动**（要补就是改规格，见 `TECH_SPEC §9.7.1`）。
- ⚠️ **"分支名只许英文"是另一个产品口径**：做法是反过来**只放行 ASCII（白名单）**，不是拉黑同形码位（几十个，永远拉不完）。别与"对齐 git"混为一谈。

**先跑红再修**（这次的红是预判过的）：加完断言 **15 条全红** —— ③b「禁用字符 + 组合记号」8 条 + 文案去重 7 条，正是预判的两处。
**新增 3 条单测**（GitDuoKit 556 → **559**）：
- ③b 组合记号在**后**必须拦（循环全部禁字符）+ 反向 `\u{0301}~` 的守卫；
- ③c **反证"没有误伤"**：全角同形字 / 中文 / emoji / 分解形式 `e\u{0301}` / 不间断空格 / 全角空格 一律放行；

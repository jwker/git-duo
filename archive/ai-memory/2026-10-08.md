### 六处判断（均已写进代码文档）

1. **决策 #57 落到实处**：`detail` 失败 ⇒ 整页换失败块（`PageFailure`）；`comments` 失败 ⇒ **只塌评论区**，头部与正文照旧，评论区自带重试。两者**各有各的出口**（`refresh()` / `retryComments()`）。合成一个"页面状态"的下场是评论拉失败时正文一起消失 —— 那是两件不同的事。
2. **`start()` 先读草稿、再取数**：草稿读本地 `UserDefaults`（快），取数是网络（慢）。反过来做的表现是"先看到一个空输入框、过一会儿字自己冒出来"，而那一瞬用户很可能已经开始打字，第一个字符会与旧草稿拼在一起。
3. **草稿随输入落盘**（`draft.didSet`）。三选一的论证写进了类型文档：只在"发送失败"那一刻存 ⇒ 用户改的几个字丢了；只在"离开页面"存 ⇒ `onDisappear` 在 App 被系统回收时不一定跑得到。落盘成本是一次 `UserDefaults` 写（几十字节），比"琢磨什么时候存才不会漏"便宜得多。
   ⚠️ 配套守卫：**恢复草稿时不能触发保存**（`isRestoringDraft`），否则 `savedAt` 会被改写成"刚进页面的时间"，而那个时间戳的用途正是"这条草稿是什么时候写的"。
4. **评论整份替换、不追加**：重取回来的就是这一页的全部；"新旧合并"要先解决去重，而那个问题只有分页加载才需要面对。
5. **已有内容时下拉刷新失败 ⇒ 一条 toast**（`RefreshCopy.failed`），**不把整屏变成失败态**（§8.5）。
6. **新建 Issue 页"几乎没有状态"正是重点**：不发任何取数请求 ⇒ 没有骨架期、没有失败档。
   - "进页面即空草稿"**由构造保证**（每次推入都造新 VM）⇒ **不设 `start()`**：多一个"忘了调用就带着上一页内容"的分支。
   - **不设 `canSubmit`**：标题空 ⇒ 用占位标题照发，正文空 ⇒ 不带 `body` 字段照发，而"按钮灰着 + 没有解释"比"发出去一条标题为「新 Issue」的"更坏（§4.10 与原型都没这一档，加了就是**替用户拍板**）。
   - `removeLabel(_:)` 与 `toggleLabel(_:)` **分开**：胶囊行上那颗一定是已选的，走 `toggle` 结果相同，但语义是两件事（`toggle` 将来若加"最多选 N 个"这类约束，胶囊行不会变成"点了没反应"）。
   - **"返回上一页"不在 VM 里**：提示属于操作结果（VM 知道结果），退页属于导航 ⇒ 视图用 `@Environment(\.dismiss)`，**不用 `Router.pop()`** —— 后者作用的是**当前选中的 Tab**，在这一层用它等于把"这一页在哪条栈里"变成一条隐含假设。

### 六处判断（均已写进代码文档）

1. **`commits` / `files` 不是"一个分区一个子状态机"**：它们各自是 `LoadState<Page<…>>`，而 `segment` 只是"现在看哪一格"。分区取数**只在 `.idle`（从没试过）时发** ⇒ 切回来不重发；失败后的重发**归按钮**，不自动重试。
2. **刷新时"当前那一格若取过就一并重取"**，判据是 **`hasFinished`**（取过就算、**失败也算**）而不是 `value != nil` —— 上次失败的那一格也该跟着刷。
3. **`markingMerged(at:)` 为什么必须收成领域层的一条规则**：`PUT /merge` 的响应体里**没有 PR 对象**，本地要变三处（`state` / `mergedAt` / 由前两者派生的 `canComment`）。第三处漏掉的表现是"刚合并完还能继续评论"，而**屏幕上看不出来**。⚠️ 只改这两样，**不伪造 `updatedAt`** —— 准确性交给下一次下拉刷新。
4. **合并的三种结局分开说**：`.merged` ⇒ `markingMerged` + `PullCopy.mergedToast`；`.notMergeable` ⇒ `mergeNotMergeableToast`；`catch` 里 **409 单独判** ⇒ `mergeConflictToast`（`PullAction.merge` 的说明写明"409 照旧抛错"），其余 ⇒ `ActionCopy.failed`。
5. **确认合并时"先关弹层、再发请求"**：提示条挂在 Tab 层，弹层盖着看不见 —— 否则用户点了确认只会看到弹层消失，然后**没有任何反馈**。

## 切片 8.2 · 数据层（写通道：`PUT` / `DELETE` contents · 建 PR）

施工图 8.2 那一行：`GitHubRepoContentEndpoint` 加**写** · `GitHubRepoPullsEndpoint` 加 `createPull` ·
**写后缓存失效** · 配额桶显式声明 + 单测（含"**不带 `branch` 的请求发不出去**"这条正面断言）。
**本片第一次真的往 URL 上挂写方法** ⇒ 三条"错了都不报错"的性质全部做成了断言。

### 端点：两个写方法 + 一个建 PR

```swift
public func putFile(owner:repo:path:message:content:Data, sha:String?, branch:String) async throws -> FileWriteResultDTO
public func deleteFile(owner:repo:path:message:sha:String, branch:String) async throws
public func createPull(owner:repo:title:String, head:String, base:String) async throws -> PullDetailDTO
```

- **`branch` 是 `String`、无默认值** —— 决策 #65（官方默认值 = 仓库默认分支 ⇒ 在 `feature/x` 上编辑却提交到 `main`、
  全程无错误信号）在**签名上就传不进来**。这是本片最该被钉住的那条。
- **`sha` 是 `String?`，为 `nil` 时整条键不写**（不是写 `null`）—— `body["sha"] == nil` 有正面断言。
  更新时它必须是**用户读到的那一版**（决策 #64 乐观锁：提交前现取 ⇒ 并发改动永远撞不上 409 ⇒ 静默丢远端改动）。
- 内容 `content.base64EncodedString()`，**不含换行**（中文 + 换行、PNG 魔数 `[0x89,0x50,…]` 两组逐字节还原）。
- `createPull` 三必填（决策 #67）；`head` 同仓库时**只写分支名**（`owner:branch` 是跨仓库 fork 写法）⇒ 断言 `head` **不含 `:`**。

### 写后缓存失效（本片唯一"看不见"的一处，最容易做错）

`HTTPRequest.invalidatesPathPrefixes` → `HTTPResponseCache.invalidate(pathPrefix:)`，
三条前缀：`/repos/{o}/{r}/contents` · `/repos/{o}/{r}/commits` · `/repos/{o}/{r}/branches`。

⚠️ 它按 URL **path** 匹配、**不看查询串** ⇒ 是**粗粒度**的：一条 `contents` 前缀会把该仓库**所有分支**的缓存一起带走
（`?ref=feature/x` 也命中）。这是**有意的**：写之后哪条分支被动了，客户端不去猜。
⚠️ 但也**不误伤别的仓库** —— 测试里往缓存放了一条 `/repos/o/other/...`，断言写后 `memoryEntryCount == 1`（只剩它）。
⚠️ 已核实过的两条配套事实：`HTTPTransport` 只在调用方没指定时补 `Content-Type: application/json`（上传二进制要覆盖它就是为这个留的）；
`GitHubURLSession.noCache()` 那条铁律不受影响（`URLSession` 仍不挂 `URLCache`，被清的永远是**自建那层**）。

### 三条"静默"性质（本片最值钱的三个断言）

| 性质 | 错了会怎样 | 怎么钉住 |
|---|---|---|
| **写永不自动重试** | `HTTPMethod.isSafelyRetryable` **只认 GET** ⇒ 重放 PUT 会因 sha 过期回 409，**而第一次其实已经写成功** ⇒ 用户看到"假失败" | 断言**带对照组**：同一套桩件下 GET `requestCount == 2`、PUT `== 1`（没有对照组，上面那条正面断言说明不了什么） |
| **`FileWriteResultDTO` 两个 sha 不能混** | `content.sha`（新 blob 基准）vs `commit.sha`（这次提交）；混了 ⇒ **第二次编辑必 409** | 断言 `blobSHA == "blob-new"` / `commitSHA == "commit-new"` / 彼此 `!=` |
| **缓存失效不误伤别的仓库** | 清多了 ⇒ 每次编辑后别的仓库全要重取（配额） | 缓存里放另一个仓库一条，断言写后只剩它（见上） |

### "不带 `branch` 的请求发不出去"这条怎么写 —— 一半写不出断言

施工图原文要求这条正面断言。**运行时断言只能覆盖"值对不对"，"传不了"是编译期事实**（`branch: String` 无默认值）。
处理办法 = 在测试里把这句**拆成两半讲清**：
上半句「少传编译不过」**由签名保证、写不出断言**；下半句断言「值真的是 `feature/x` 且 `!= "main"`」。
注释里点明：少了下半句，用户看到的就正是决策 #65 那条静默错。

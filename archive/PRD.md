## 1. 产品概述

- **产品**：GitDuo 2.0 —— 通用 GitHub 移动客户端。
- **形态**：**纯 iPhone 版**（本期不考虑折叠屏与 iPad）。
- **目标用户**：日常使用 GitHub 参与协作的开发者（个人项目 + 团队仓库）。
- **底部导航**：4 个 Tab —— 首页 / 仓库 / 探索 / 我的。（**通知本期不做**，见 §8.2）
- **核心心智**：**仓库是一切的中心**。自己的仓库是"可写工作台"（浏览代码、编辑文件、提交、管理分支、处理 Issue 与 PR）；他人的仓库是"只读阅览室"（Star / Watch / Fork / 收藏 + 浏览，无写操作）。
- **设计原则**：
  1. **单手可达**：核心操作集中在拇指区，采用 Tab + 推入栈的导航，不做反直觉的手势导航。
  2. **内容优先**：正文（README / diff / 评论）占据最大面积，装饰性元素最小化。
  3. **快**：以缓存与条件请求控制流量与配额，性能是一等需求。
  4. **真实感**：完整的空态、加载态、错误态，任何失败都有出口（重试 / 提示 / 重新登录）。

## 2. 信息架构与导航

### 2.1 导航模型 ✅

- **每个 Tab 各维护一条独立导航栈**，切换 Tab 时保留各自的栈状态（返回后回到原层级）。
- **推入 / 返回**：从列表或卡片进入下级页面为「推入」，页面顶部提供返回操作回到上一级。
- **转场**：推入时新页面从右侧进入，被压住的上一层页面左移并降低透明度。
- **页面形态两种**：

| 形态 | 使用场景 | 结构 |
|---|---|---|
| Tab 页 | 首页、仓库、探索、我的 | 无返回栏；含大标题；内容区可上下滚动 |
| 推入页 | 其余全部页面 | 顶部返回栏（返回 + 居中标题）；内容区可滚动 |
| 全屏流程页 | 登录页、GitHub 授权页 | 无返回栏、无 Tab 栏；**未登录时整体覆盖主界面**，完成或退出后才露出主界面 |

- **渲染后行为**：进入页面后可执行的必要动作，如自动聚焦搜索框、自动记录最近访问、初始化列表等。
- **前置流程优先级**：登录页与授权页（§4.0）不属于任何 Tab 的导航栈；只要处于未登录状态，主界面与底部 Tab 栏即不可见、不可操作。

### 2.2 底部 Tab 栏 ✅

| 顺序 | 名称 | 图标 |
|---|---|---|
| 1 | 首页 | home |
| 2 | 仓库 | folder |
| 3 | 探索 | compass |
| 4 | 我的 | user |

- 当前 Tab 高亮（图标与文字变深色）。
- **本期无 Tab 角标**：原「通知」Tab（含未读数字角标）本期不做，见 §8.2。

### 2.3 弹层与轻提示 ✅

- **弹层**：从底部升起，带半透明遮罩；点击遮罩或完成动作后关闭。全部弹层见 §5。
- **轻提示**：深色胶囊提示，展示约 2.4 秒后自动消失，用于操作结果反馈（如"已 Star""已切换分支"）。

> 以下为产品需处理的核心数据对象与字段定义。表格中的取值均为**示例**，用于说明字段含义。

### 3.1 仓库 `Repo`

| 字段 | 含义 |
|---|---|
| 全名 | `owner/name` |
| 描述 | 仓库简介 |
| 主语言 | 如 Swift / Rust |
| 语言色 | 该语言的品牌色（用于色点与占比条） |
| Star 数 | 显示为字符串，大数可缩写（如 `124k`） |
| Fork 数 | 同上 |
| 是否私有 | 布尔值；私有仓库需展示「私有」标记 |
| 可写权限 | 布尔值；**当前登录用户对该仓库是否拥有写权限**——这是「自己的仓库 / 他人仓库」的唯一判定依据（§6.1） |

- 新建标签提供 **10 色色板**供选择。

### 3.9 收藏夹 `Folder`

| 字段 | 含义 |
|---|---|
| 名称 | — |
| 项目数 | 收藏的项目数量 |
| 是否默认 | 内置「默认收藏夹」标记；带此标记的收藏夹不可重命名、不可删除 |

- 收藏夹属于**本机数据**（仅自己可见），与仓库的 Star 互不影响。
- 重命名 / 删除在「我的收藏」管理页完成（§4.19）。

### 3.10 分支

- **当前分支**：**按仓库分别记忆**的浏览状态——同一条链上「代码」与「Commits」共用它，**仓库之间互不影响**。
- **解析规则**（进入任一仓库时生效）：
  1. 该仓库上次用过的分支**仍存在** → 沿用它；
  2. 该分支**已不存在**（被删除 / 改名）→ **回落该仓库的默认分支**；
  3. **从未访问过**该仓库 → 直接用其默认分支。
- 任何情况下都**不会把别的仓库的分支名带进来**（不存在"仓库 B 显示仓库 A 的分支"的状态）。
- 分支记忆属**账号绑定数据**，**跨启动存活**，退出登录时清空。
  （"退出登录时清空"这条本身就要求它必须活过进程重启——否则无从谈起。落盘口径与解析的两段式见 TECH_SPEC §9.4.1 与决策 #55。）
- 分支列表（可切换、可管理）。

### 3.11 搜索

| 项 | 定义 |
|---|---|
| 搜索范围 | 4 个：仓库 / 用户 / 代码 / Issue · PR |
| 热门关键词 | 提供一批热门词供快捷填入 |
| 搜索历史 | 本机保留最近 8 条 |
| 搜索状态 | `{ 关键词, 当前范围 }`；切换范围保留关键词 |

### 3.12 探索筛选

| 维度 | 选项 | 未选时显示 |
|---|---|---|
| 日期范围 | 今天 / 本周 / 本月 | `日期` |
| 编程语言 | Swift / Rust / TypeScript / Python / Go | `语言` |
- 日期范围默认「本周」；语言默认不选（不选即全部）。
- **不含「交流语言」维度**：GitHub 公开 API（REST / GraphQL）不提供该字段与搜索限定符，该维度仅存在于 GitHub Trending 网页（URL 参数 `spoken_language_code`）。为避免探索页依赖网页抓取（无契约、易碎），该筛选项**本期不实现**。

### 3.13 首页数据

| 数据 | 定义 |
|---|---|
| 置顶仓库 | **读取 GitHub 个人主页的置顶仓库**（只读，最多 6 个），与网页端保持一致 |
| 最近访问 | 打开过的仓库，最新排最前，最多保留 6 条；**本机记录**，GitHub 不提供该数据。⚠️ 2026-10-15 起每条还落盘**记录时刻已知的 owner 头像地址**（走查第 72 条）—— 取数成功后补记；旧记录没有该字段 ⇒ 那一行回退首字母兜底圆 |

**两个入口都必须带上「可写性」**（2026-10-06 补）：置顶卡片与最近访问行都要决定点进去是「自己的仓库」（§4.4，可编辑）还是「他人仓库」（§4.13，只读浏览），而可写性是**进入之前**就要定下的判定依据（§6.1：唯一依据 = 当前登录用户对该仓库是否拥有写权限）。原型的 `PINNED` 演示数据里就**混着一个他人仓库**（`rust-lang/rust`），正是为了走通这条分流。

- **置顶仓库**：可写性**随置顶一起取回**。它在 GitHub 上就是"你对这个仓库有什么权限"这个既存事实，与名称、Star 数同源，不需要额外请求。
- **最近访问**：本机只存仓库全名是不够的 —— 所以**写入这条记录时，把"当时打开的是哪一种页面"一并记下来**。那条信息在打开的那一刻就是确定的（打开的是自己的仓库 ⇒ 可写；打开的是他人仓库 ⇒ 只读），**不需要任何额外请求，也不需要事后猜**。
- ⚠️ **不许用"仓库全名是不是以我的登录名开头"来判定**。这个近似在 Fork / 组织仓库 / 协作者仓库上都会判错，而判错的表现是"点进自己的仓库却没有编辑入口"，或反过来"给他人仓库长出编辑入口、改完才吃 403"。

### 4.0 前置流程：登录与授权（全屏页）

> 未登录时 App **只呈现这两屏**，底部 Tab 栏不可见、不可操作；授权成功后进入主界面。设置页「退出登录」（§4.20）可回到第一屏。

#### 4.0.1 登录页（全屏页）

**入口**：首次启动；凭据失效（令牌被撤销 / 刷新失败）后自动回到本页；设置页「退出登录」后回到本页。

**结构（自上而下）**：
1. **品牌区**：GitHub 标记方图 + 产品名「GitDuo」+ 定位语（「为 iPhone 打造的 GitHub 客户端」/「代码 · Issues · Pull Requests 一站浏览」）。
2. **权限预告卡片**：标题「登录后 GitDuo 会申请」，下列 6 条：
   - 仓库内容 · 读取代码 / 文件树；提交、新建、上传文件（读写）
   - Issues · 查看、创建、评论、开关（读写）
   - Pull Requests · 查看、创建、评论、合并（读写）
   - Star 收藏 · Star / 取消 Star 仓库，读取 Starred 列表（读写）
   - 关注关系 · 关注 / 取关用户（读写）
   - 账号基本信息 · 读取公开资料、贡献数据与关注列表（只读）
3. **主操作**：「使用 GitHub 登录」按钮（GitHub 深色样式，含 GitHub 标记）。
4. **安全说明**：授权在系统浏览器中完成 · 密码不经过 GitDuo；令牌存于本机 Keychain，**退出登录即同时撤销 GitHub 侧授权**（也可随时在 GitHub 设置中撤销）；**安装页须选择「All repositories（全部仓库）」**，否则 GitDuo 只能看到被勾选的那部分仓库（见 §6.1）。

**交互**：
- ✅ **「使用 GitHub 登录」** → 进入授权页（§4.0.2）。
- ✅ 页面**不提供**账号密码输入、第三方登录、注册入口。

**跳转**：
- 授权成功 → 主界面（默认落在首页）。
- 用户取消授权 → 停留在本页，可重试。

**功能点**：
- 未登录首屏：启动时若本机无有效凭据即进入本页；底部 4 Tab 此时不可用。
- 权限预告：列出的 6 项即实际申请的范围，与授权页清单**逐条一致**（不虚报、不遗漏，见 §6.1）。
- 登录方式：仅 GitHub 一种。
- 安全：令牌只写本机 Keychain、可一键清除；**退出登录时会一并撤销 GitHub 侧的授权**（§5.11）。
- 退出后：「我的 → 设置 → 退出登录」清空本机凭据并回到本页。

#### 4.0.2 GitHub 授权页（全屏页 · 系统浏览器）

**入口**：登录页点击「使用 GitHub 登录」。

**结构（自上而下）**：
1. **系统浏览器容器**：顶部栏为「取消」+ 地址「🔒 github.com」。
2. **授权确认区**：GitHub 标记 + 标题「Authorize GitDuo」+ 说明「my-git 想要访问你的 @{登录名} 账户」。
3. **权限清单**：6 条，每条含资源名 + 范围，与登录页权限预告**完全一致**。
4. **授权说明**：「GitDuo 由 my-git 开发，将获得以上权限；你随时可以在 GitHub 设置的 Applications 中撤销访问。」
5. **主操作**：「Authorize my-git」（绿色主按钮）。

**交互**：
- ✅ **「Authorize my-git」** → 转入「正在完成授权…」加载态（加载指示 + 回调地址 + 换取令牌说明）→ 成功后关闭全屏页，进入主界面并提示「已登录」。
- ✅ **「取消」**（顶部栏）→ 返回登录页，**不留下任何凭据**。

**跳转**：
- 成功 → 主界面（首页）。
- 取消 → 登录页。

**功能点**：
- 授权页**由 GitHub 托管**，在系统浏览器视图中呈现（非应用内自绘网页），以复用系统登录态并防钓鱼。
- 权限清单与登录页同一套，避免"预告"与"实际申请"不一致。
- 授权后的加载态对应「接收回调 → 换取令牌 → 写入 Keychain」三步。
- 取消 / 拒绝授权的唯一出口是**回到登录页**，可重试。
- **授权回调的安全性**：授权完成后的回调**只带回一次性授权码，不携带任何令牌**；该授权码必须在 GitDuo 内部、配合只存在本机且从不外传的校验信息，才能换取访问令牌。因此即便回调在中途被其他应用截获，也无法凭它获得访问权限；并且每一步都需要用户在 GitHub 页面上明确同意，**不存在"静默授权"路径**。

### 4.2 搜索页（推入页）

**入口**：首页 / 仓库 / 探索三页右上角搜索图标（同一页面）。

1. 搜索输入框（放大镜图标 + 输入框 + 清除按钮）；进入时自动聚焦。
2. 范围分段：仓库 / 用户 / 代码 / Issue · PR。

**交互**：
- ✅ **边输边搜**：输入即刷新结果（刷新结果区时保持输入焦点与光标）。
- ✅ **回车**：把关键词记入「最近搜索」（最多 8 条）并给出提示；关键词为空时提示先输入。
- ✅ **点开任一条结果也记入「最近搜索」**（2026-10-07 补：按原型校正 —— PRD 原先只写了回车，而原型在回车（`commitSearch`）与点开结果（`openSearchRepo` / `openCodeFile` / `openConvRow`）**两处都记**。点开才是"这条搜索有用"的真实信号）。
- ✅ **清除按钮**：清空输入并重新聚焦。
- ✅ **切换范围**：只按新范围重筛当前关键词，不丢失输入（也不清空已加载的页）。
- ✅ **空闲态**（未输入）：展示「最近搜索」（点一条直接复用关键词；可清除本机记录）+「热门关键词」标签（点即填入）。
- ✅ **「清除」不弹确认层**（直接清 + 提示 `已清除搜索记录`）—— 与「最近访问」的「清除全部记录」**有意不同**：那是浏览足迹，这是用户显式输入的关键词，意图明确。
- 无搜索历史时展示空态 `还没有搜索记录`。

**结果渲染**：
- 结果标题：`{范围名} · {N} 个结果`。**N 是服务端匹配的总数**（GitHub 的 `total_count`，与网页端一致），不是屏幕上已加载的条数。
- **分页**：首屏 30 条；还有下一页时，列表底部给一个 **「加载更多」按钮**（不自动加载 —— 搜索配额很紧，用户可控的续页更安全）。结果总数上限 1000 条（服务端硬限）。
  - ⚠️ **「Issue · PR」范围一次要取两路**（GitHub 对 App 用户令牌的限制：Issue 与 PR **不能在一次查询里同时拿回**）⇒ 该范围首屏是 **30 条 Issue + 30 条 PR**，先 Issue 后 PR 依次排列，底部按钮一次续两路。
- **加载态**（§8.5 三档）：首屏骨架屏 / 续页时按钮内联 loading 并禁用 / 失败时底部一行错误 + 可重试。
- 无结果：`没有匹配「{关键词}」的{范围名}` / `换个关键词，或切换上方范围试试`
- ⚠️ **代码范围的特殊门槛**：它**必须**含至少一个关键词（只填 `language:swift` 这类限定符服务端不接受）⇒ 结果区显示 `先输入关键词`，**不发请求**。其余三个范围不受此限。

| 范围 | 数据源 | 匹配字段 | 结果行去向 |
|---|---|---|---|
| 仓库 | 全部仓库（含趋势仓库去重） | 名称 + 描述 + 语言 | 进入对应仓库页 ✅ |
| 用户 | 用户列表 | 用户名 + 昵称 + 简介 | 打开用户资料弹层（§5.10）✅ |
| 代码 | 代码索引 | 路径 + 代码行 + 仓库 + 语言 | 打开只读文件页 ✅ |
| Issue · PR | Issue 列表 + PR 列表 | 标题 + 标签/编号 + 分支 | 进入 Issue 详情 / PR 详情 ✅ |

- 代码结果行：文件路径、`{仓库} · {语言}`、等宽字体代码预览行。
- Issue·PR 结果行：状态图标、标题、`{仓库} #{编号}`、状态胶囊。

**功能点**：四个范围（切范围只筛当前关键词，不丢输入）；边输边搜（回车记录）；结果可点（四类去向）；历史最多 8 条、可清除。

### 4.8 分支管理（推入页）

**入口**：代码页（§4.4.1）面包屑上的分支胶囊，切换弹层内点「管理分支…」。

**结构**：
1. 分区标题：`{仓库} · 全部分支（N）`——本页**只列当前仓库的分支**。
2. 分支列表（菜单卡片）：分支名；当前分支显示「当前」胶囊；**非默认分支**带「删除」按钮（默认分支不可删）。
   - ⚠️ 2026-10-07 补：**受保护分支同样不给删除按钮**（决策 #53）。GitHub 的删除分支接口对受保护分支会**直接失败**，照"非默认就画"会在那种分支上给出一个必然报错的按钮，而报错文案解释不了"为什么别人能删我不能"。
3. 「＋ 新建分支」按钮。
4. 「合并分支到 {当前分支}…」按钮。
5. 说明：`Merge 走 API · 冲突时引导到网页端处理`。

**交互**：
- ✅ 点分支行 → 切换当前分支（只影响本仓库）。
- ✅ 「删除」：删除前需校验是否有未合并提交；**若删除的是当前分支，自动回落该仓库默认分支**并提示。
  - ⏳ 校验细节已在 2026-10-07 定下（决策 #53）：比较「该分支」与「默认分支」，**只要该分支有未合并提交（`ahead_by > 0`）就阻止删除**并提示。原「待细化」一项由此关闭。
- ⏳ 「新建分支」：输入名称 → 从当前分支创建并切换。
  - **名称在客户端先校验**（服务端不合法时只回一个 422，那不像表单校验、容易被读成"服务器坏了"）：不能为空；不能含空格与 `~ ^ : ? * [ \`；不能含控制字符；不能以 `/` 或 `.` 开头 / 结尾；不能含 `//` 或 `..`；不能以 `.lock` 结尾；不能是 `HEAD`。
- ✅ 「合并分支…」→ 打开**合并分支弹层**（**不是**「提交更改」弹层，2026-10-07 拍板，决策 #52）：源分支选择器 + 目标分支（当前分支，只读）+ 提交信息（可选）+ 合并按钮 + 冲突引导。
  - **为什么偏离原型**：原型与本文原先都写"打开提交更改弹层（标题 `合并 {源} → {当前}`）"，但那个弹层的内容是「提交信息 + **提交到当前分支 / 新分支 + PR**」——「新分支 + PR」这一项对合并没有对应语义；且原型里源分支是**自动挑第一个非当前分支**，用户选不了，而"哪条分支合进哪条"恰是这个操作的唯一关键输入。

⚠️ **"只是没有维护者操作"这句在 2026-10-09 之后不再准确**：GitHub 的规则是"谁提的谁可关"（决策 **#79**）⇒ 他人仓库里**我提的** Issue 照样能关、能重开；只在这个仓库里**别人提的** Issue 上才是只读（操作区只有一行提示）。

**结构**：
1. 头部卡片：状态胶囊 + 状态说明（`该 Issue 仍然开放` / `已于 {时间}关闭`）+ 标题 + `#{编号} · {仓库} · 由 {创建者} 创建于 {时间}`。
2. 评论区：多条评论（头像、作者、时间、正文，正文支持行内代码）。
3. 评论输入区（占位「写评论… (Markdown 支持)」+「发送」按钮）。
4. 发送失败提示条（默认隐藏）。
5. **操作区**（2026-10-09 新补，见下）。

**操作区**（2026-10-09 用户走查报回「从「我的 Issue」进详情后不能改状态」⇒ 规格从"本页不做"改为"做"；正本 `TECH_SPEC §9.8`、决策 **#79**）：

| 条件 | 操作区 |
|---|---|
| 我**不是**作者、且对这个仓库没有写权限 | 一行提示 `他人仓库 · 可评论参与讨论，关闭 Issue 需维护者权限` |
| 可以管 + 仍然开放 | 「关闭 Issue」→ 确认弹层（§5.18） |
| 可以管 + 已关闭 | 「重新打开 Issue」（**不弹确认**） |

⚠️ **那一行提示与 §4.14 的列表页脚不是同一句**（尽管只差一个分隔符）：这一句说的是"**这一页的操作区为什么没有按钮**"（` · `），页脚说的是"**这个列表能做什么**"（`：`）—— 原型的 PR 详情页与两个列表页脚也是这样分开的（`08-pr.js:50` 对 `10-explore-repo.js:108` / `:123`）。取舍写在 `IssueCopy.readOnlyHint` 的文档里，别合并那两句。

- ✅ **判据 = 我是这条 Issue 的作者 ∨ 我对这个仓库有写权限**。依据是 GitHub 的规则（官方原文逐字：*"Anyone can close an issue they opened. Repository owners, collaborators on repositories owned by a personal account, and people with triage permissions or greater on repositories owned by an organization can close issues opened by others."*）。
  - ⚠️ **由此，「我的 Issue」页里每一条都能关** —— 那个列表的口径是 `author:@me`、每一条都是我提的，**哪怕它落在别人的仓库里**。这既是用户报回那条的修法，也是本页判据**不看"仓库是不是我的"**的理由：只看"是不是我提的"会把别人的仓库里我提的 Issue 判成只读，而那恰恰是他报的那一条。
  - ⚠️ **登录名比较必须大小写不敏感**：GitHub 登录名本身大小写不敏感（`JiangJiang` 与 `jiangjiang` 是同一个人）。按字符串直接比会让"我自己提的 Issue"认不出自己 ⇒ 那条 Issue 变成只读，而屏幕上看起来**完全正常**。
- ✅ **关闭 / 重新打开**：`PATCH /repos/{o}/{r}/issues/{n}`，`state` 取 `closed` / `open`；响应是**完整的 Issue 对象** ⇒ 直接用它替换本地那一份（与 §4.11 对 PR 的处置同一条：只在本地改一个字段，会造出"界面说已关闭、服务端说还开着"）。
- ⚠️ **关闭要二次确认、重新打开不要**（有意不对称）：关掉之后所有关注这个仓库的人都会看到"已关闭"，而重开只是把状态还原、没有可损失的东西。
- ⚠️ **另一处不对称（与 §4.11 比，2026-10-09 用户裁定）**：「关闭 Issue」**有**确认弹层，而 §4.11 的「关闭 Pull Request」**没有**（原型就是直接关）。两页做的是同一件事、形态却不同 ⇒ **记在这里当有意不同，别当缺陷报**。它的来源是用户对 Issue 侧的裁定（决策 **#79**），而 PR 侧那一片是按原型落的、当时没有这个议题。

**交互**：
- ✅ **「发送」**：发送中给出处理反馈；失败时在输入区上方显示红色提示条 `⚠ 发送失败：网络不可用。草稿已保留，可重试。`，并保留草稿供重试。

- ✅ **关闭 / 重新打开**见上面的操作区（2026-10-09 起本页有了这两个动作 —— 此前那条"本页不做、规格未给"的登记**已作废**，正本见决策 **#79**）。

### 4.11 Pull Request 详情（推入页）

**入口**：仓库详情 PR 分区；搜索 Issue·PR 结果；我的页「我的 Pull Request」；探索 PR 列表。

  - ⚠️ **那枚「已批准」胶囊来自「评审」、不是评论本身**（2026-10-08 明确）：审批状态与会话评论在 GitHub 是两份不同的数据，在这里按作者与时间合进同一条时间线。
- 操作区（🔒 按状态与权限区分）：

| 条件 | 操作区 |
|---|---|
| 他人仓库 | 文字提示 `他人仓库 · 可评论 Review，合并 / 关闭需维护者权限` |
| 自己的仓库 + 开放 | 「合并 Pull Request」→ 合并弹层（§5.3）；「关闭 Pull Request」✅ |

**分区二：Commits**：提交列表，行 → 提交详情（🔒 透传只读状态）。

**分区三：文件**：
- 提示：`{N} 个文件 · 点击文件卡片展开 diff`。

### 4.14 探索 Issues 列表（推入页）

**入口**：探索仓库详情「参与协作」→ Issues。

**结构**：说明行 `{仓库} · 开放 {N} 个`；Issue 卡片列表；底部说明 `他人仓库：可评论参与讨论，关闭 Issue 需维护者权限`。

**范围与计数**（2026-10-06 拍板）：
- ✅ **只列开放式** Issue。说明行写的就是「开放 {N} 个」、页脚写的是「关闭 Issue 需维护者权限」—— 混入已关闭的会让标题与内容对不上；要看已关闭的走仓库网页端。
- ⚠️ `GET /issues` 的返回里**混着 PR**（GitHub 把 PR 当作一种 Issue），要按 `pull_request` 字段滤掉。**一页 30 条里可能只有 9 个是 Issue**，这是端点固有行为，不是缺数据。
- ✅ `{N}` = **已加载的非 PR 条目数**（还有下一页时显示 `30+`）。**不显示**接口里那个"开放 Issue 数"字段 —— 它把 PR 也算进去，会比屏幕上实际看到的条数多，而"数字对不上"会被读成"这个 App 数不准"。

**空态**（2026-10-07 拍板）：`暂无开放的 Issue` / `这个仓库当前没有开放中的 Issue`（`EmptyBox` 两行式，与首页两处同构）。

⚠️ 空态时**说明行保留、页脚不显示**：
- 说明行照旧渲染（写作 `{仓库} · 开放 0 个`）—— 它交代的是"这个仓库确实一个开放的都没有"，
  与空态框说的不是同一件事（前者是**计数结论**，后者是**状态**）。
- 页脚 `他人仓库：可评论参与讨论，关闭 Issue 需维护者权限` 讲的是"能对这个列表做什么"，
  列表为空时它无所指，是废话 ⇒ 不渲染。

**交互**：✅ 卡片 → Issue 详情。

### 4.15 探索 PR 列表（推入页）

**入口**：探索仓库详情「参与协作」→ Pull Requests。

**结构**：说明行 `{仓库}`；PR 卡片列表；底部说明 `他人仓库：可评论 Review，合并 / 关闭需维护者权限`。

**范围**（2026-10-06 拍板）：✅ **只列开放式与已合并**，每行按状态换图标。
⚠️ **已关闭但未合并的不列**（2026-10-07 明确）：`state=all` 把三种都取回来，本地滤掉"已关闭未合并"那一档 ——
GitHub 没有"open + merged"这一个筛选项，`state=open` 又会把已合并的一起排除掉。过滤放在 `LoadRepoPulls`。
- 与「探索 Issues 列表只列开放式」**有意不对称**：PR 的「已合并」是一个有价值的**结局**，而 Issue 的「已关闭」只说明没人做了；且本页的入口副标题就是「查看他人贡献」，已合入的 PR 正是贡献最直接的证据。
- ⚠️ GitHub **没有独立的"已合并"状态**（`closed` 之下不再细分），判定靠"关闭且带合并时间"。

**空态**（2026-10-07 拍板）：`暂无 Pull Request` / `这个仓库还没有任何 Pull Request`。

⚠️ 说明行保留（它本来就只有仓库全名、没有计数）、页脚不显示 —— 处置与理由同 §4.14。

**交互**：✅ 卡片 → PR 详情（**只读模式**）。

### 4.21 我的 Pull Request / 我的 Issue（推入页）

**入口**：我的页菜单卡片一的「我的 Pull Request」与「我的 Issue」——**两个菜单项、同一个页面**，只有标题与筛选口径不同。

**结构**：
1. `inline` 标题：`我的 Pull Request` / `我的 Issue`。
2. 说明行：`{N} 个结果` —— `{N}` 是**服务端返回的匹配总数**（与 GitHub 网页搜索一致，不是"已加载条数"）。
3. 结果列表：每行 = 标题 + 状态胶囊 + `{仓库全名} #{编号} · {相对时间}`。
   **与搜索页的 Issue / PR 结果行是同一行**，不另做一版（同一个 UI 两处定义必然分叉）。
4. 底部「加载更多」按钮（有下一页时出现）。

**交互**：
- ✅ 点一行 → 该行的详情页（PR 详情 §4.11 / Issue 详情 §4.9；两个菜单项各自只会出现一种类型）。
- ✅ 「加载更多」→ 续下一页；没有下一页时按钮消失（结果上限 1000 条，与 GitHub 一致）。

**范围与口径**：
- 两个页面都**只列自己创建的**，PR 与 Issue **各自一页、不混排**（决策 #73）。
- **排序 = 最近更新降序**（不是"最佳匹配"）：点进这一页的人想看的是"我最近提的 / 最近有动静的"，
  而默认相关度排序对"按作者查"这种查询给不出可预期的顺序。
- ⚠️ **与搜索页「Issue · PR」范围不是同一个东西**：搜索页那个范围在 App 用的令牌类型下**必须拆成两条查询再合并**，
  落成的是一个 Issue / PR 混排列表；本页每一项只回答一个问题（"我提了哪些 PR" / "我提了哪些 Issue"）。
- 分页用**「加载更多」按钮**（与搜索页一致，不滚到底自动加载）：两者走同一个搜索配额桶（30 次/分钟），
  滚动自动加载会很快打满它（决策 #44 的理由在此同样成立）。

**空态**（2026-10-09 定，两行式，与探索页两处同构）：
- 我的 Pull Request：`还没有创建过 Pull Request` / `在任意仓库里发起一个 Pull Request，它就会出现在这里`
- 我的 Issue：`还没有创建过 Issue` / `在任意仓库里创建一个 Issue，它就会出现在这里`

> ⚠️ **本页不提供「开放 / 已关闭」分段**（2026-10-09 登记为有意偏差第 **39** 条）：加状态筛选会把说明行那个 `{N}` 变成"开放数"，
> 而这一页要回答的是"我提过多少"；真要做分段就得再发一条查询、配额翻倍 ⇒ 本期不做。

### 5.1 清除最近访问确认
- 标题：`清除最近访问记录？`

- 按钮：`清除全部记录`（红底）/ `取消`。

### 5.2 标签选择 / 新建
- 上段「选择标签」：仓库全部标签列表，点击多选（已选绿色 ✓），操作后刷新标签行与弹层。
- 下段「新建标签」：名称输入框 + **10 色色板**（单选高亮）+「创建并选中」按钮。

### 5.3 合并 Pull Request
- 标题：`合并 · {分支流向}`。
- 三种合并方式（单选，默认第一项）：
  - `Merge commit` — 保留全部分支提交历史
  - `Squash and merge` — 压成一个提交，历史更干净
  - `Rebase and merge` — 线性历史，不含合并节点
- 「确认合并进 {目标分支}」→ 状态置为已合并。
- 底部提示：`Merge 走 API · 分支有冲突时引导到网页端处理`。

### 5.4 探索筛选
- 标题：筛选维度名（日期范围 / 编程语言）。

### 5.5 选择收藏列表
- 标题：`选择收藏列表`。

### 5.6 新建收藏夹
- 标题：`新建收藏夹`。
- 名称输入框 +「创建并收藏」按钮。
- 校验：空名 → **弹层内那一行**（通则）；重名 → 提示已存在并自动选中，且**关掉弹层**（那句走提示条）。创建后自动把当前仓库收藏进新收藏夹。

> 「`上传图片 · 相册` → **选中图片的文件名**」。那句在该系统 API 下**做不到** ——
> 核实 iOS 27.0 SDK（`_PhotosUI_SwiftUI`）里 `PhotosPickerItem` 的**全体成员**只有：
> `itemIdentifier`（相册内部的资源标识，形如 `UUID/L0/001`）、`supportedContentTypes`、
> `loadTransferable(type:)`（只交字节，不附名字）。**没有任何一条给出文件名。**
> ⇒ 规格改成"App 生成"，规则收在 `UploadFileName.photo(fileExtension:now:)`（有单测）：
> 时间戳到秒（相隔一秒就不会重名，而重名在这条通道上是一条**硬失败** —— 服务端 422），
> 扩展名取自 `supportedContentTypes.first.preferredFilenameExtension`
> 并做小写 / 去空白 / `jpeg`→`jpg` 归一化，拿不到时兜底 `jpg`
>（一个没有扩展名的文件在 GitHub 上会被当成二进制文件，看不见也预览不了）。
> 处置方式与决策 #47 同源：**外部事实优先，改规格、不改实现**。
> `文件 App` 那一条**不受影响** —— `URL.lastPathComponent` 拿得到真实文件名。

- ⚠️ **路径是自动定的、界面上要看得见**：提交弹层顶部多一行**只读**说明 `将写入 {路径}`
  （原型没有这一行 ⇒ 登记为有意偏差）。理由是"东西存到哪"是这一步里用户唯一可能搞错的事，
  而它是 App 决定的 —— 不露出来用户就只能靠猜。**这一行不是输入框**，改路径请改用「新建文件」。
  ⚠️ 它显示的路径**必须与真正写下去的是同一个**（都走 `RepoDetailViewModel.uploadDestination`）——
  两处各算一次的那天，说出来的和做出来的会不一样。
- ⚠️ **相册图片取原始字节、不重编码**：用户上传的是"这张图片"，重编码会改内容与体积。
  ⚠️ **2026-10-09 收窄（决策 #71）**：这条**只在 ≤1MB 时成立** —— 见下面那条。
  ⚠️ **同日再收窄一次（决策 #72）**：**≤1MB 且格式本来就能在网页端显示**才成立 —— HEIC 之类的**照样要转**（见下下条）。
- ✅ **超过 1MB 的图片：先自适应压缩**（2026-10-09 补，**决策 #71**）—— 原先这一档只有"提示并引导网页端"，
  而**真实照片动辄 >1MB** ⇒ 相册这条出口对大多数照片形同虚设。改法：

  | 源图 | 怎么压 |
  |---|---|
  | **PNG / 带 alpha** | **先只缩最长边**（2048 → 1600 → 1200 → 800 共 **4 档**，保住截图的锐利与透明通道）；穷尽后转 JPEG |
  | **其余**（HEIC / JPEG / WebP 等） | **先逐档降 JPEG 画质**（0.9 → 0.8 → 0.7 → …），仍超再缩最长边 |
  | **动图（多帧）** | **不压** —— 压完只剩第一帧，那是"改内容"而不是"压体积" |

  - 目标 = `SaveFile.maxContentBytes`（1MB）；**≤1MB 的图片仍然原样上传**，不重编码
    （⚠️ **例外：格式在网页端显示不出来的** —— 那种≤1MB 也要转，见下下条）。
  - ⚠️ **不承诺"一定压到 1MB 以内"**：超大像素图、以及已经重度压缩过的 JPEG，到画质 / 尺寸下限**仍可能超限**
    ⇒ 那一档落到本弹层底部那句提示（引导网页端；网页端拖拽上传走的是另一条通道，上限 25MB）。
  - ⚠️ **压过的必须让用户看见**：提交弹层（§5.9）里多一句 `已压缩 3.2MB → 0.8MB`。
  - ⚠️ **代价**：压缩**有损**；重编码会**剥掉 EXIF（含 GPS 位置）**、PNG 转 JPEG 还会**丢透明**
    ⇒ 传上去的**不再是相册里那一份**。这正是原先定"取原始字节"的理由，现在为了"这条出口能用"而让位 ——
    两侧的代价都已写在本节与 `REVIEW-CHECKLIST` 的有意偏差表里。
- ✅ **网页端显示不出来的图片格式：自动转码**（2026-10-09 补，**决策 #72**）—— 前一节只解决了"体积"，**"格式"这一层原先全文没写**。
  而 iPhone 相机默认拍的是 **HEIC**，浏览器根本渲染不出来 ⇒ 传上去在 GitHub 页面上就是**一块破图**，用户还得自己去查为什么。
  改法：**凡是不在下面这张白名单里的图片，一律转成名单内的格式**；⚠️ **判据是 ImageIO 从字节读出的真实类型**（改过名的、没有扩展名的都算得准）：

  | 类别 | 格式 | 怎么办 |
  |---|---|---|
  | **白名单（不动）** | PNG / JPEG / GIF / WebP / SVG | **一个字节都不改** —— 它们在网页端本来就显示得出来，转了只会丢信息 |
  | **要转 → PNG** | 带 **alpha 通道**的（任何格式）；以及源本身 **无损** 的（TIFF / BMP / 单帧 GIF） | 无损→无损，多数还更小；透明只有 PNG 装得住 |
  | **要转 → JPEG** | 其余有损源（**HEIC / HEIF / RAW(DNG)** …） | 体积效率最高的可渲染格式 |

  - ⚠️ **不是"一律转 PNG"**：PNG 是无损编码，一张 2MB 的 HEIC 转 PNG 可能到 15MB ⇒ 多数会被缩到 800px 甚至更小才塞得进 1MB，
    而画质并不会比转 JPEG 好。这就是"按源选"的理由。
  - ⚠️ **名单短一点是刻意的**：名单外的格式只会"多转一次"（用户看到一句 caption），而名单里混进一个**其实显示不出来**的格式，
    代价是"传上去是一块破图、用户还不知道为什么"。所以 `AVIF` **有意留在名单外**（它浏览器渲染得出来，但不在 GitHub 那份文档里）。
  - ⚠️ **≤1MB 也照转**（这一条是本节的**用户原话**，也是唯一一处**与"≤1MB 原样上传"直接冲突**的地方 ⇒ 上面那条已相应收窄）。
  - ⚠️ **文件名扩展名跟着换**：`IMG_1234.HEIC` → `IMG_1234.jpg`。不换的话 GitHub 仍按**老扩展名**去渲染，等于白转。
  - ⚠️ **代价**：转码**必然重编码** ⇒ 剥掉元数据（含 EXIF / GPS）、RAW 会丢掉相机原始信息；**体积也可能变大**（见下面那句 caption 的第三种说法）。
    两侧代价同样已在 `REVIEW-CHECKLIST` 的有意偏差表里登记。
  - ⚠️ **动图仍然不转**（同上面那条：多帧压完只剩第一帧 = 改内容）。
- ⚠️ **超过 1MB 且压不动**（或根本不是图片）⇒ 按本弹层底部那句话提示并引导网页端，**不静默失败**。
- ⚠️ **重名不静默覆盖**：落点那一层已存在同名文件时提交会被服务端挡下，提示"已有同名文件，请改名或到网页端处理"。

### 5.9 提交更改
- 标题：`提交更改 · {来源}`。来源取值：`新建文件` / `编辑 {文件名}` / `上传文件（文件 App）` / `上传图片（相册）`。
- 提交信息输入框（占位「提交信息（commit message）」）。
- 目标分段（默认第一项）：
  - `提交到 {当前分支}`（默认）

- 「提交」按钮：
  - 提交到当前分支 → 完成提交。
  - 新分支 + PR → 创建新分支并自动打开 PR。
  - 提交信息为空时使用默认信息（`update via GitDuo`）。
  - 提交后若当前页为编辑器则自动返回。
- 底部提示：`冲突保护：提交遇 409（远端已更新）时，可选查看最新版或强制覆盖`。

✅ **2026-10-08 补齐三处（切片 8）**：

**① 来源为上传时，多一行只读的 `将写入 {路径}`**（理由见 §5.8）。
⚠️ **2026-10-09 补**：这一行下面**在图片被压过 / 转过时**多一句 caption（**决策 #71⑤ · #72⑤**）——
同一条理由（"App 替你决定了什么"要露出来）；⚠️ **三种情况三种说法，不许合成一句**：

| 发生了什么 | 那一句 |
|---|---|
| 只是压小了 | `已压缩 3.2MB → 0.8MB` |
| 压小了，**而且**换了格式 | `已压缩并转为 JPEG · 3.2MB → 0.8MB` |
| **只换了格式**（体积可能反而变大） | `已转为 JPEG · 1.2MB → 1.4MB` |

⚠️ 第三种存在的理由：**转码有时会把文件变大**（HEIC 转 PNG 尤其明显），那时说"已压缩"就是**假话**。
⚠️ 什么都没发生（≤1MB 且格式显示得出来 / 非图片）**不出现这一句**。
⚠️ 两种数字（原字节 / 最终字节）都是**实测**，不是算出来的。

**② 选「新分支 + PR」时多出两行输入**（原先只有一句提示条）：
建分支要有**分支名**、建 PR 要有 **PR 标题**，而这两样原先在界面上**没有任何来源**
（`POST /pulls` 的 `title` / `head` / `base` 三个都是必填）⇒ 两行输入**随提示条一起出现**：

| 输入 | 预填值 | 说明 |
|---|---|---|
| 分支名 | `gitduo/{yyyyMMdd-HHmmss}` | 从哪条分支分出去 = **当前分支**（不可改，那就是"新分支 + PR"的定义） |
| PR 标题 | 提交信息（为空则为默认信息 `update via GitDuo`） | PR 的 `base` = 当前分支、`head` = 上面那个新分支名 |

⚠️ 两行都**可以改**。不给输入的话这两个值就完全由 App 决定，而它们都是**要留在仓库历史里**的东西
（分支名会在分支列表与网页端一直挂着、PR 标题是别人看到的第一行）。

**③ 409（远端已更新）的两个出口就地在弹层里换出来**：
- `查看最新版` —— 取回最新的内容与版本，把**你的改动与新版一起给出来**，你合完再提。
- `强制覆盖` —— 丢掉远端那一次改动、以你现在的内容为准。⚠️ **危险操作，需二次确认**。
- ⚠️ 409 只说明"这个文件在你看它之后被别人（或者你自己的另一台设备）改过"，
  文案**不得断定"是别人改的"**。
- 「查看最新版」之后**不自动重提** —— 用户得先看到新版长什么样。

**④ 「新分支 + PR」是多步操作，失败时要说清做到了哪一步**（2026-10-08 补齐）：
- 分支建好了、提交失败 ⇒ 必须说出「`{新分支}` 已创建，但改动未提交」（**分支确实已经在那儿了**，
  否则用户再点一次会撞上"分支已存在"而不知道为什么）。
- 提交成功、PR 没建起来 ⇒ 必须说出「改动已提交到 `{新分支}`，PR 未创建」并给网页端出口。
- ⚠️ 这两种情形下**不"整体回滚"**（不会去把刚建的分支删掉）—— 分支上可能已经有用户的提交，
  删分支会连带删掉它。

### 5.16 重命名文件
- 标题：`重命名文件`。
- 路径输入框（**预填当前完整路径**）+「保存」/「取消」。
- 说明行：`重命名会移动文件 · 原路径将不再存在`。
- 校验（都在客户端先拦，不拿服务端 422 当表单校验）：
  - 路径为空 → 提示 `先输入文件路径`。
  - 与当前路径相同 → 直接关闭，不提示（同 §5.13 的做法）。
  - 目标路径上**已存在文件** → 提示 `该路径上已有文件`；**不覆盖、不合并**。
  - 目标路径的目录不存在 ⇒ **允许**（服务端会自动创建目录，与 §4.6 新建文件同一口径）。
- 执行：**两步、按顺序** —— 先写入新路径，成功后再删掉旧路径。
  - 两步都成功 → 提示 `已重命名为 {新路径}`，并返回文件查看页（该页路径跟着变）。
  - 第一步就失败 → 提示失败原因，**什么都没变**。
  - 第一步成功、第二步失败 → ⚠️ 提示 `新路径已写入，原路径仍在` ——
    这一刻**仓库里确实有两个文件**，必须说出来（含糊其辞会让用户以为只成功了一半）。
- ⚠️ **本版不支持重命名目录**（只做单文件的路径变更）。

- 标题：`删除「{文件名}」？`。
- 说明：`删除会立即在 {当前分支} 上生成一次提交，本机不做二次备份。`
- 按钮：`删除文件`（红底）/ `取消`。
- 警告行：`此操作不可撤销（可在 GitHub 网页端的提交历史里找回）`。
- 确认后：该文件从当前分支移除并提示 `已删除 {文件名}`，返回上一级目录列表。
- ⚠️ **删除前要现取一次版本标识**（服务端要求带它才肯删），这一步对用户不可见；
  拿不到（文件已被别人删掉）⇒ 提示 `该文件已不存在`，**不报"删除失败"**。

### 5.18 关闭 Issue 确认（Issue 详情页触发）
- 标题：`关闭这条 Issue？`。
- 说明：`关闭之后仍然可以重新打开，评论都会保留。`
- 按钮：`关闭 Issue`（**主色，不是红底** —— 关闭不是破坏性动作，随时可以撤销）/ `取消`。
- 确认后：状态置「已关闭」、头部那句说明变成 `已于 {时间}关闭`，并提示 `已关闭 #{编号}`。
- ⚠️ **「重新打开」不弹这个弹层**（理由见 §4.9 操作区末条：重开没有可损失的东西）。
- ⚠️ **请求失败时状态一个字都不改**，只在页面上报一句 `操作失败，请重试` ——
  关不掉却把界面画成"已关闭"，是这一页最难被发现的一种错（头部说明会跟着变成假的）。

## 6. 横切能力

### 6.1 权限模型 🔒（核心）

**权限从哪来**：应用的权限在**首次授权时一次性确定**。登录页（§4.0.1）向用户预告、GitHub 授权页（§4.0.2）正式申请，两处列出的**六项完全一致**：

| 申请的资源 | 范围 | 支撑的能力 |
|---|---|---|
| 仓库内容 | **读写** | 代码与文件树浏览；新建 / 上传 / 编辑文件、提交、分支管理 |
| Issues | 读写 | Issue 列表 / 详情 / 新建 / 关闭 / 评论 / 标签 |
| Pull Requests | 读写 | PR 列表 / 详情 / 评论 / 合并 / 关闭 |
| Star 收藏 | 读写 | Star / 取消 Star 仓库；Starred 分段与「我的 Star」列表 |
| 关注关系 | 读写 | 用户资料页的关注 / 取关 |
| 账号基本信息 | 只读 | 个人资料、贡献数据、关注列表 |

- 除这六项外**不申请任何其他权限**（尤其不申请通知、组织、密钥、仓库管理等）。
- 后两项是**账号级权限**，只作用于"你与仓库 / 用户的个人关系"，**不构成对任何仓库内容的读写能力**——对代码的写权限仍然只来自「仓库内容」一项。
- ⚠️ **令牌可见范围（安装范围）**：GitHub App 的令牌可见范围 = **用户自身权限 ∩ 应用声明权限 ∩ 安装时勾选的仓库**。因此**安装页必须选择「All repositories（全部仓库）」**；若只勾选部分仓库，首页、仓库列表、搜索、Starred 会一起缺数据，且现象隐蔽（表现为"我的仓库少了一部分"）。该引导文案写在登录页安全说明中（§4.0.1）。
- 应用内**不提供单项权限开关**：用户要么整体授权，要么整体撤销（退出登录，§5.11）。
- 申请了写权限 ≠ 处处可写：是否真的能写，仍由下面的仓库归属规则决定。

**判定规则**：当前用户对仓库是否拥有写权限 = **自己的仓库**（可写）／**他人仓库**（只读）。**依据是仓库数据中的「可写权限」字段（§3.1），不按仓库名、所属账号或任何静态名单判断**——因此「自己的仓库」的准确含义是"用户拥有写权限的任意仓库"，他人协作仓库（被授予写权限）同样算自己的。

| 能力 | 自己的仓库 | 他人仓库 |
|---|---|---|
| 详情页 | 可写详情页（**枢纽页 + 四个入口页**，§4.4） | 只读浏览页（**功能集不同**） |
| 代码 / 文件浏览 | ✅ | ✅（只读） |
| 分支切换浏览 | ✅ | ✅（只读，无管理） |
| 分支创建 / 删除 / 合并 | ✅ | ❌（提示需先 Fork） |
| 新建 / 上传 / 编辑文件 | ✅ | ❌ |
| 提交更改 / Revert | ✅ | ❌ |
| 新建 Issue | ✅ | ❌（仅可浏览、评论） |
| 关闭 Issue | ✅ | ❌（需维护者权限） |
| 合并 / 关闭 PR | ✅ | ❌（仅可评论 Review） |
| Star / Watch / Fork | ✅ | ✅ |
| 收藏 | ✅ | ✅ |

- **只读态传递**：文件页、提交详情、PR 详情进入只读模式时，🔒 隐藏相应写操作入口。

### 6.2 收藏 / Star / Watch / Fork（语义分离）✅

| 能力 | 语义 | 可见性 | 对计数影响 |
|---|---|---|---|
| **Star** | 公开星标 | 公开 | 计数 +1/−1，进入 Starred |
| **Watch** | 订阅该仓库动态 | 公开 | **仅展示订阅数**（订阅动态依赖通知，本期不做） |
| **Fork** | 复制到自己账户 | 公开 | 获得完整写权限 |
| **收藏** | **私人收藏夹**，可多列表归类 | **仅自己可见** | **不影响 Star 数** |

**收藏归类规则**：一个仓库**同时只属于一个收藏夹**（多标签式归类不做）。收藏夹右侧展示的「项目数」由归属关系推导，随动作即时变化：

| 动作 | 项目数变化 |
|---|---|
| 收藏（首次） | 目标夹 **+1** |
| 更换收藏夹 | 原夹 **−1**、目标夹 **+1**（不是两边都加） |
| 取消收藏（再点已选列表） | 所属夹 **−1** |
| 新建收藏夹并收藏 | 新夹 +1，原夹（若有）−1 |
| 重命名收藏夹 | **计数不变**（只改名字） |
| 删除收藏夹 | 该夹连同计数一并消失；其中的收藏项**回落「默认收藏夹」**，默认夹 **+N**（N = 该夹原有项目数） |

**收藏两段式交互**：
1. 首次点「收藏到我的列表」→ 立即收藏进「默认收藏夹」，并提示「再点可选择列表」。
2. 已收藏后按钮变为「已收藏 · {列表名}」→ **再点才**打开选择收藏列表弹层。

**收藏夹管理**：「我的 → 我的收藏」（§4.19）可对**自建**收藏夹重命名与删除；内置「默认收藏夹」带默认标记，不可重命名 / 不可删除。收藏夹是**本机数据**，不调用任何接口，与 Star 计数完全无关。

### 6.3 搜索系统 ✅
- 四范围、边输边搜、回车记录、刷新结果时保持输入焦点、历史最多 8 条。详见 §4.2。
- 首页 / 仓库 / 探索三处共用同一搜索页。

### 6.4 分支与提交链路 ✅
- 两处进**代码页**的入口都带**分支切换**（显示当前分支）—— 自己的仓库那档还给「管理分支…」，他人仓库那档只给一句只读说明。
- 当前分支是**按仓库分别记忆**的状态（不是全局唯一值）：同一仓库内代码浏览与 Commits 随之联动；换到另一个仓库时按 §3.10 的解析规则取该仓库自己的分支，**记忆失效则回落其默认分支**。
  - ⚠️ **2026-10-14 改了口径，但结论不变**：代码页与 Commits 页各在一个页面里，
    "联动"不再靠同一份内存状态，而是靠**落盘的记忆 + 两页永不共存**（§4.4.5）。不是"断开了"，是换了条路。
- 提交链路：编辑 / 新建 / 上传 → 提交更改弹层 → 选目标（当前分支 / 新分支 + PR）→ 提交。
  - 「新分支 + PR」要**建分支 + 提交 + 建 PR 三步**，中途失败时提示说清"做到了哪一步"（§5.9）。
- 文件操作：文件查看页的「更多」打开文件操作菜单 → **重命名**（移动文件，原路径不再存在）/ **删除文件**（不可撤销）—— 见 §5.15–§5.17。
- 提交详情 → Revert（**跳转网页端完成**，不在客户端构造反向提交）。

### 6.5 标签系统 ✅
- 仓库级标签库 + 新建标签（名称 + 10 色）。
- 新建 Issue 时多选；新建标签后加入仓库标签库，全仓库可复用。

### 6.6 通知与角标【本期不做】

通知能力整体不做，因此本版本**无 Tab 角标**、无未读态联动、无通知类型图标。原设计（Tab 角标 = 未读通知数；单条已读 / 全部已读实时联动角标；5 类类型图标：PR、Issue、已关闭 Issue、提交、发布）留待后续迭代。见 §8.2。

### 6.7 最近访问记录 ✅
- 进入任意仓库详情（自己的 / 他人的）后自动记录，最新排最前，最多 6 条。
- 首页「清除」可清空（带确认），只影响本机历史，不影响置顶仓库（置顶来自 GitHub 个人主页，与本机历史无关）。

## 7. 文案与空态规范

**空态**
- 首页置顶：`GitHub 个人主页还没有置顶仓库` / `去个人主页「Customize your pins」挑几个，回到首页下拉即可看到`
- 首页最近访问：`暂无访问记录` / `打开任意仓库后会自动出现在这里`
- 搜索历史：`还没有搜索记录`
- 搜索无结果：`没有匹配「{关键词}」的{范围}` / `换个关键词，或切换上方范围试试`
- 探索无结果：`没有符合条件的仓库，试试放宽筛选`
- 探索仓库详情的三个「数据拿到了但是空的」（2026-10-06 定）：
  - 语言构成（空仓库 / 只有配置文件）：`暂无语言数据`
  - Latest Release（从没发过版本）：`还没有发布过版本`
  - 贡献者（一个也没有）：`暂无贡献者`
  - ⚠️ 三处都是**分区保留 + 标题下一行灰字**，不是把分区整块抹掉 —— 分区在不在本身也是一条信息。
- 代码目录：`空目录`
- 探索 Issues 列表（仓库一个开放的都没有）：`暂无开放的 Issue` / `这个仓库当前没有开放中的 Issue`
- 探索 PR 列表（仓库一个 PR 都没有）：`暂无 Pull Request` / `这个仓库还没有任何 Pull Request`
  - ⚠️ 这两处**说明行保留、页脚不显示**（2026-10-07 定）—— 理由见 §4.14。
- 我的 Star（一个都没 Star 过）：`还没有 Star 过任何仓库` / `在仓库页点一下 Star，它就会出现在这里`
- 我的 Pull Request / 我的 Issue（自己一个都没创建过）：`还没有创建过 Pull Request` / `在任意仓库里发起一个 Pull Request，它就会出现在这里`（Issue 同理换词）
  - ⚠️ **后两处是 2026-10-09 新定的**（切片 9 才有的页面，原型里没有）。与探索页两处**有意不同**：那两处说的是"**这个仓库**没有"（状态），
    这两处说的是"**你**还没有"（归属），所以第二行要给出"怎么做才会有"，而不是解释现状。

**登录与授权**
- 登录页定位语：`为 iPhone 打造的 GitHub 客户端` / `代码 · Issues · Pull Requests 一站浏览`
- 登录页权限卡标题：`登录后 GitDuo 会申请`
- 登录页主按钮：`使用 GitHub 登录`
- 登录页安全说明：`授权在系统浏览器中完成 · 密码不经过 GitDuo` / `令牌存于本机 Keychain，退出登录即同时撤销 GitHub 侧授权` / `安装页请选「All repositories（全部仓库）」`
- 授权页标题：`Authorize GitDuo`；说明：`my-git 想要访问你的 @{登录名} 账户`；主按钮：`Authorize my-git`
- 授权进行中：`正在完成授权…` / `已收到回调，正在换取令牌并写入本机`
- 授权页顶部栏：`取消`

**提示 / 校验**
- `先输入关键词` / `已清除搜索记录` / `搜索「{关键词}」`
- `已登录 · 欢迎回来，@{登录名}` / `已退出登录 · 已同时撤销 GitHub 侧授权`（降级：`已退出登录 · 本机令牌已清除（未能撤销 GitHub 侧授权，可在设置中手动撤销）`）
- `登录已过期，请重新授权`（令牌被撤销或刷新失败时）
- `请先填写标签名称` / `标签已存在，已为你选中` / `已创建标签 "{名称}"`
- `先输入收藏夹名称` / `收藏夹已存在，已为你选中` / `已创建收藏夹「{名称}」`
- `已从收藏移除` / `已收藏到「{列表}」（私人收藏夹）`
- `已重命名为「{名称}」` / `已有同名收藏夹` / `收藏夹已存在` / `已删除收藏夹「{名称}」· {N} 项已回落到「默认收藏夹」` / `「默认收藏夹」不可删除`
- `先写点内容再发送` / `评论已发送`
- `已切换分支` / `已删除分支 {分支}` / `已删除分支 {分支} · 已回到 {默认分支}`（删除的是当前分支时）
- `置顶仓库在 GitHub 个人主页管理 · 已为你打开`
- `已清除最近访问记录`（清除弹层确认后）
- `已 Star · 公开星标，仓库计数 +1` / `已取消 Star · 仓库计数 −1`（Star 按钮切换后）
- `GitDuo 未被授权访问该仓库，暂不能 Star`（**2026-10-09 新定**，走查 #3 定案）
  - ⚠️ **它不是"操作失败"的另一种说法，而是一句成因说明**：GitHub App 的用户令牌只对
    **安装范围内**的仓库写得了 Star（实测：自己的仓库 204、别人的仓库 403
    `Resource not accessible by integration`）。⇒ 它**只覆盖这一种成因**，
    其余失败仍走通用那句 `操作失败 · 请重试`（本句按成因判，见 TECH_SPEC §3.5.4 的判定口径）。
  - ⚠️ **三处共用同一句**（§4.4 头部 / §4.13 头部 / §4.18 行）：两个位置放得下，
    所以它同时做**置灰说明**与**读屏提示**；放不下的那一处（§4.18）只做失败提示。
    逐字不许改 —— 它出现在两个详情页的头部，改一处就会两页不一致。
- `{筛选维度}：{值}` / `{筛选维度}：已取消，显示全部`（探索筛选；维度为 `日期范围` / `编程语言`）

**列表说明行**
- 探索榜结果不完整：`结果可能不完整（GitHub 计算超时）· 下拉刷新重试`
  - ⚠️ 它是**说明**不是错误：已加载的条目照常可用，只是这一页少了些本该在里面的仓库。

**错误态**
- 评论发送失败：`⚠ 发送失败：网络不可用。草稿已保留，可重试。`
- 提交冲突（409）：`远端已更新，可选查看最新版或强制覆盖`

## 8. 交付范围与实现要求

### 8.1 需完整实现的能力（不得停留在入口或提示）

| 能力 | 要求 |
|---|---|
| 登录与授权 | 需真实走完授权码流程：系统浏览器内完成授权 → 校验回调 → 换取令牌 → 写入本机 Keychain；取消 / 失败 / 令牌失效均有明确出口 |
| 登录状态持久化 | 凭据安全保存，重启后免重复授权；令牌失效时自动回到登录页 |
| 首页置顶仓库 | 需真实读取 GitHub 个人主页的置顶（GraphQL `pinnedItems`）并展示；客户端不提供增删（见 §8.2） |
| 仓库列表分段筛选 | 全部 / 公开 / 私有 / Starred 需真实过滤 |
| 仓库详情 Issues / PR 分段 | 开放 / 已关闭 / 已合并 / 筛选需真实过滤 |
| 探索筛选 · 日期范围 | 需按真实时间窗取数，而非仅换算文案 |
| 文件上传（文件 App / 相册） | 需接文件选择器与上传能力；单个文件 ≤1MB 直接提交，更大的文件引导到网页端 |
| 文件历史 / Raw / 重命名 / 删除 | 需真实能力（删除带 SHA 校验） |
| 分支新建 / 删除 / 合并 | 需真实 Git 操作；合并冲突引导到网页端；删除当前分支后需回落该仓库默认分支 |
| 分支状态（按仓库） | 每个仓库各自记住自己的当前分支，换仓库不得串用；进入时校验该分支仍存在，失效则回落默认分支（见 §3.10） |
| 用户「关注」「查看公开仓库」 | 需真实能力（关注 / 取关依赖「关注关系」账号级权限） |
| 贡献热力图 | 需接入真实贡献数据 |
| Star 管理页取消 Star | 需真实取消并联动计数（依赖「Star 收藏」账号级权限；Starred 分段亦同源）。⚠️ **2026-10-15 起页内取消入口暂不渲染**（第 70 条：列表行按钮先去掉，领域机制保留）—— Star / 取消 Star 的操作入口只剩仓库详情页头部 |
| 收藏夹管理 | 新建 / 重命名 / 删除需真实生效，并即时同步到仓库详情页的「选择收藏列表」弹层；收藏夹为本机数据，不调用接口 |
| 收藏夹项目数 | 需随归属变化真实增减：收藏 +1、换列表「原夹 −1 且目标夹 +1」、取消收藏 −1、删除夹时其中项回落默认夹（见 §6.2） |
| 设置项（主题 / 清除缓存 / 退出登录） | 需真实设置行为 |
